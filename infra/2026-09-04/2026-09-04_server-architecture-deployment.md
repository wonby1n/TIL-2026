# 서버 구성, 로드 밸런싱과 배포 전략

## 기본 서버 구성

```text
🧑 사용자
 │ HTTPS
 ▼
🌐 Nginx
 │ Reverse Proxy
 ▼
☕ Spring
 │ SQL
 ▼
🗄️ DB
```

- **EC2**: 프로그램이 실행되는 가상 컴퓨터
- **Nginx**: 외부 요청을 먼저 받아 내부 서버에 전달하는 리버스 프록시
- **Spring**: 비즈니스 로직과 API 처리
- **DB**: 영구 데이터 저장

Nginx는 HTTP 요청을 HTTPS로 리다이렉트하고 TLS 연결을 처리하거나, 경로에 따라 요청을 서로 다른 서버로 전달할 수 있다.

## 동일한 Spring 서버를 여러 개 실행하는 이유

```text
             ┌─▶ ☕ Spring A
🧑 → 🌐 Nginx ┼─▶ ☕ Spring B
             └─▶ ☕ Spring C
```

- 요청 분산과 처리량 확대
- 한 서버 장애 시 다른 서버를 통한 서비스 지속
- 배포 중 다른 서버를 통한 요청 처리

동일한 서버들이 모두 요청을 처리하면 **Active-Active**, 하나가 처리하고 다른 하나가 대기하면 **Active-Passive** 구조라고 할 수 있다.

모든 컨테이너가 하나의 EC2에 있다면 EC2 장애 시 모두 중단된다. 장애 대비를 위해서는 컨테이너 수만 늘리는 것이 아니라 여러 호스트나 가용영역으로 장애 범위를 분리해야 한다.

## 로드 밸런싱과 헬스체크

로드 밸런서는 요청을 여러 서버에 분산한다. 헬스체크를 통해 실제 요청을 처리할 수 없는 서버를 대상에서 제외할 수 있다.

```text
⚖️ Load Balancer
 ├─ ☕ Spring A ✅
 └─ ☕ Spring B ❌ → 요청 제외
```

- Liveness: 프로세스 자체가 살아 있는가?
- Readiness: 실제 요청을 받을 준비가 되었는가?

## 배포 전략

- **Recreate**: 기존 버전을 끄고 새 버전 실행
- **Rolling**: 서버를 순서대로 새 버전으로 교체
- **Blue-Green**: 구버전과 신버전 환경을 준비하고 트래픽 전환
- **Canary**: 일부 트래픽부터 신버전으로 보내며 점차 확대

```text
🔵 Blue: 기존 버전 서비스 중
🟢 Green: 새 버전 실행·검증
                 │
          헬스체크 성공
                 ▼
        트래픽을 Green으로 전환
```

Blue-Green은 배포 전략이고 로드 밸런싱은 트래픽 관리 기술이다. 트래픽 전환에는 Nginx나 관리형 로드 밸런서를 사용할 수 있다.

## 안전한 CI/CD 흐름

```text
Git Push
  ▼
빌드 → 테스트
  │ 실패: 중단
  ▼ 성공
Docker 이미지 생성
  ▼
Green 환경 실행
  ▼
헬스체크
  │ 실패: Blue 유지
  ▼ 성공
트래픽 전환
```

테스트가 실패하면 배포 단계는 시작하지 않아야 한다. 기존 서버를 먼저 내린 뒤 빌드하면 빌드 실패 시 서비스가 중단된 채 남을 수 있으므로, 새 버전을 먼저 준비하고 확인한 뒤 전환해야 한다.

## 로그와 메트릭

- **로그**: 개별 요청과 오류가 어떻게 발생했는지 확인
- **메트릭**: CPU, 메모리, 응답시간, 오류율 등 전체 상태의 변화 확인

```text
📊 메트릭으로 이상 시간 발견
          ▼
📝 해당 시간의 로그로 원인 조사
```

## 핵심 요약

> 좋은 서버 구성은 컨테이너 개수를 늘리는 것이 아니라 요청을 분산하고, 장애를 감지하며, 새 버전을 검증한 뒤 안전하게 트래픽을 전환하도록 장애 범위를 분리하는 것이다.
