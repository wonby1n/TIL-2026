# AI 서비스 성능과 운영

## 프롬프트 캐싱

매 요청에 동일한 시스템 지침이나 긴 문서를 반복해서 전달하면 입력 토큰 처리 비용과 지연시간이 커질 수 있다. 프롬프트 캐싱은 반복되는 공통 부분을 재사용하는 방식이다.

```text
공통 내용: 시스템 지침·사내 규정 → ♻️ 캐시 가능 영역
개별 내용: 사용자의 새로운 질문 → 매번 처리
```

실제 적용 조건과 과금 방식은 모델 제공사마다 다르므로 사용하는 API 문서를 확인해야 한다.

## 배칭

배칭은 여러 추론 요청을 묶어서 한 번에 처리하는 방식이다. GPU 처리량과 비용 효율을 높일 수 있지만, 요청이 모일 때까지 기다리면 개별 사용자의 지연시간이 늘어날 수 있다.

```text
요청 A ─┐
요청 B ─┼─▶ 하나의 배치 ─▶ GPU
요청 C ─┘
```

따라서 실시간 상담처럼 응답시간이 중요한 기능과 대량 문서 처리처럼 처리량이 중요한 작업은 서로 다른 기준으로 설계해야 한다.

## 양자화

양자화는 모델의 가중치를 더 작은 숫자 형식으로 표현해 모델 크기와 연산량을 줄이는 기술이다. 제한된 메모리의 모바일 기기에서 실행하는 온디바이스 AI나 GPU 자원이 제한된 환경에서 유용할 수 있다.

- 장점: 모델 크기와 메모리 사용량 감소, 추론 속도 향상 가능
- 주의점: 모델에 따라 정확도가 낮아질 수 있으므로 적용 후 평가 필요

## Rate Limiting과 Backpressure

외부 LLM API나 자체 GPU 서버가 처리할 수 있는 양보다 요청이 많이 들어오면 일부 요청을 제한하거나 대기시켜야 한다.

```text
요청 폭주 → 🚦 Rate Limiter
             ├─ 허용 → AI 서버
             ├─ 대기 → Queue
             └─ 거절 → 429 응답
```

- **Rate Limiting**: 일정 시간 동안 받을 요청 수를 제한한다.
- **Backpressure**: 소비자의 처리 속도보다 요청 생성 속도가 빠를 때 생산자에게 감속이나 대기를 요구한다.

## 분산 추적과 Correlation ID

AI 요청 하나가 Spring, AI 서버, 벡터 검색, 외부 LLM API를 거치면 각 시스템의 로그만 따로 보아서는 병목 구간을 찾기 어렵다. 동일한 요청 식별자를 각 구간에 전달하면 요청의 전체 이동 경로를 연결할 수 있다.

```text
request-id: abc123

📱 앱 → ☕ Spring[abc123] → 🤖 AI 서버[abc123]
     → 🔎 벡터 검색[abc123] → ☁️ LLM API
```

## 핵심 요약

> AI 운영에서는 정확도만이 아니라 토큰 비용, 처리량, 지연시간, 요청 제한과 요청 단위의 추적 가능성을 함께 관리해야 한다.
