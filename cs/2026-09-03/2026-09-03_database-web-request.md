# 데이터 저장소 선택과 웹 요청 흐름

## 관계형 DB와 NoSQL

NoSQL은 단순히 SQL 문법을 사용하지 않는 DB라는 뜻이 아니라, 관계형 테이블 모델을 중심으로 하지 않는 여러 데이터베이스를 묶어 부르는 표현이다.

### 관계형 DB가 자연스러운 경우

- 데이터의 관계와 구조가 명확함
- 주문·결제·송금처럼 정합성이 중요함
- 여러 변경을 하나의 트랜잭션으로 처리해야 함

### 문서형 NoSQL이 자연스러울 수 있는 경우

- 상품별 상세 속성처럼 데이터 구성이 다양함
- 유연한 스키마가 필요함
- JSON과 유사한 문서 형태로 묶어 다루기 편함

```json
{"name":"노트북","cpu":"i7","ram":16}
```

```json
{"name":"티셔츠","color":"black","size":"L"}
```

문서형 DB는 JSON 파일을 폴더에 저장하는 것과 다르다. MongoDB 같은 DB가 문서의 저장·검색·수정·삭제를 관리한다.

## 트랜잭션과 정합성

- **정합성**: 관련 데이터가 서로 모순되지 않는 상태
- **트랜잭션**: 여러 변경을 하나의 논리적 작업으로 묶는 단위
- **커밋**: 모든 작업이 성공했을 때 변경 확정
- **롤백**: 작업 중 하나라도 실패했을 때 변경 취소

```text
주문 저장 ✅
재고 차감 ✅
결제 기록 ❌
      ↓
전체 롤백
```

세 작업이 이미 하나의 트랜잭션으로 올바르게 묶였다면 주문만 저장된 채 남아서는 안 된다. 외부 결제 시스템처럼 하나의 DB 트랜잭션으로 묶기 어려운 작업은 별도의 처리 방법이 필요하다.

## 캐시와 TTL

캐시는 자주 읽는 데이터를 빠르게 반환하기 위해 원본보다 가까운 곳에 임시 저장한다.

```text
첫 요청  → 캐시 없음 → DB 조회 → 캐시에 저장
다음 요청 → 캐시에서 바로 반환
```

**TTL(Time To Live)**은 캐시 데이터의 유효시간이다. 원본 가격이 바뀌어도 기존 캐시를 삭제하거나 갱신하지 않으면 TTL이 끝날 때까지 이전 가격이 보일 수 있다.

## API 요청 흐름

```text
📱 앱
 │ HTTPS 요청
 ▼
🌐 Nginx
 │ 요청 전달
 ▼
☕ Spring API
 │ SQL 실행
 ▼
🗄️ DB
```

앱이 DB에 직접 접속하지 않고 API 서버를 거치면 인증·권한·입력값·업무 규칙을 서버에서 통제하고 DB 인증정보와 구조의 직접 노출을 줄일 수 있다.

## HTTP 상태 코드

- `200`: 성공
- `400`: 잘못된 입력 등 요청 문제
- `401`: 인증 필요 또는 실패
- `404`: 요청한 자원을 찾을 수 없음
- `500`: 서버 내부 오류

## 온디바이스 AI와 서버 AI

```text
온디바이스: 📱 앱 안의 모델 → 스마트폰에서 추론
서버 방식:  📱 앱 → 🌐 API → 🤖 서버에서 추론 → 결과 반환
```

인터넷 없이 AI 기능이 동작하고 앱에 모델과 모바일 추론 런타임이 포함되어 있다면 온디바이스 추론일 가능성이 높다. 실제 구조는 코드 의존성, 모델 파일과 네트워크 요청을 확인해야 확정할 수 있다.

## 핵심 요약

> 저장소는 유행이 아니라 데이터 관계·정합성·구조 유연성을 기준으로 선택한다. 앱 요청은 API 서버를 거쳐 검증된 뒤 DB로 전달되며, 캐시는 자주 읽는 데이터의 응답을 빠르게 할 수 있다.
