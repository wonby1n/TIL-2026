# AI 서비스의 데이터 저장소와 검색

## 역할별 저장소

```text
📱 사용자 → ☕ Backend
               ├─▶ 🗄️ RDB: 회원·대화·결제·작업 상태
               ├─▶ 🧠 Redis: 세션·캐시·인증번호
               ├─▶ 🪣 S3: 음성·영상·이미지·문서
               ├─▶ 🔎 검색·Vector DB: 검색용 색인·임베딩
               └─▶ ☁️ 외부 LLM API
```

작은 서비스라면 처음부터 모든 저장소를 도입하지 않고 RDB 중심으로 시작한 뒤 실제 요구와 병목이 생길 때 분리한다.

## RDB

MySQL과 PostgreSQL은 모두 범용 관계형 DB다. 회원, 대화방, 메시지, 주문, 결제처럼 관계와 정합성이 중요한 데이터에 사용할 수 있다.

PostgreSQL은 `jsonb`, 복잡한 쿼리와 확장 생태계 때문에 공간·벡터·시계열 관련 구성에서 자주 선택된다. 그러나 시계열 데이터라고 무조건 PostgreSQL을 사용해야 하는 것은 아니다.

## Redis

빠르고 수명이 짧은 데이터에 활용한다.

- 로그인 세션
- TTL이 있는 인증번호
- 자주 조회하는 캐시
- 요청 횟수 제한 정보

## S3 같은 객체 저장소

큰 파일 자체는 객체 저장소에, 파일 소유자·주소·상태 같은 메타데이터는 RDB에 저장할 수 있다.

```text
실제 영상 파일 → 🪣 S3
사용자 ID·제목·S3 URL → 🗄️ RDB
```

## Elasticsearch

Elasticsearch는 많은 문서와 로그에서 내용을 빠르게 검색하고 분석하는 분산 검색 엔진이다.

```text
상품 원본·가격·재고 → 🗄️ RDB
상품 이름·설명 검색 → 🔎 Elasticsearch
```

텍스트를 분석해 역색인을 만들고 관련도에 따라 결과를 정렬할 수 있다. 로그 검색·집계, 전문 검색, 벡터 검색과 키워드 검색을 결합한 하이브리드 검색에도 활용할 수 있다.

RDB와 Elasticsearch 사이에는 동기화 지연이 생길 수 있으므로 최종 결제 가격 같은 핵심 값은 원본 RDB에서 다시 확인해야 한다.

## 시계열 데이터

시간 순서대로 계속 쌓이는 센서값, 주가, 심박수, CPU 사용률 등이 시계열 데이터다.

```text
10:00 CPU 40%
10:01 CPU 52%
10:02 CPU 87%
```

PostgreSQL은 timestamp 타입과 시간 기준 파티셔닝을 사용할 수 있다. TimescaleDB 같은 PostgreSQL 기반 확장을 사용하면 시계열 관리 기능을 강화할 수 있지만, PostgreSQL을 쓴다는 사실만으로 TimescaleDB를 사용했다고 판단할 수는 없다.

## 별도 AI 서버가 필요한 경우

외부 LLM API 호출이 단순하면 Spring Backend가 직접 호출할 수 있다. 클라이언트 앱이 직접 호출하면 API Key 노출 위험이 있다.

```text
📱 앱 → ☕ Spring → ☁️ LLM API
```

RAG, 임베딩, 문서 전처리, 복잡한 AI 워크플로 또는 직접 GPU 모델을 운영해야 한다면 별도 AI 서버를 고려할 수 있다.

```text
📱 앱 → ☕ Spring → 🤖 AI 서버
                        ├─ 문서 검색·RAG
                        ├─ 임베딩
                        └─ LLM 또는 자체 모델 호출
```

## 핵심 요약

> 데이터베이스 제품보다 데이터의 관계·크기·수명·검색 방법을 먼저 보고 저장소를 선택한다. 별도 AI 서버도 AI라는 이유로 무조건 만들지 않고 AI 로직의 복잡도와 모델 운영 필요성을 기준으로 분리한다.
